## 1. VALIDACIÓN DE FIXES — HITO POR HITO

### 🔴 Hito 5 — `en_id` no es un parámetro de ARQ · **CRÍTICO**

`apps/api/app/core/worker_enqueuer.py:58-62`:

```python
await _pool.enqueue_job(
    "discovery_run_task",
    run_id,
    en_id=f"discovery:{run_id}",   # ← ARQ no conoce este parámetro
)
```

La firma de ARQ 0.26 es `enqueue_job(function, *args, _job_id=None, _queue_name=None, ...,  **kwargs)`. El parámetro de deduplicación se llama **`_job_id`** (con guion bajo). Cualquier keyword que no empiece por `_` cae en `**kwargs` y se serializa como **argumento de la tarea**.

Al ejecutarse, ARQ invoca:

```python
discovery_run_task(ctx, run_id, en_id="discovery:...")
```

Y la firma real es `async def discovery_run_task(ctx, run_id: str)` → **`TypeError: got an unexpected keyword argument 'en_id'`**.

**Doble consecuencia:**
1. La idempotencia **no existe** — sin `_job_id`, ARQ genera uno aleatorio y los duplicados siguen siendo posibles.
2. **Ningún run se ejecuta.** El job falla al invocarse, antes de `_run_set_status(run_id, "running")`. El run queda en `pending` para siempre y el usuario no ve error.

**Fix (1 línea):**
```python
_job_id=f"discovery:{run_id}",
```

**Verificación sin gastar créditos:** encola un run y observa los logs del worker. Si aparece el `TypeError`, está confirmado. Después del fix, el run debe alcanzar `status=running`.

⚠️ El mismo error tipográfico está propagado a `ARQUITECTURA_LENS.md` v3.0 (§2, §7.4) y al prompt de esta auditoría. Hay que corregirlo en los tres sitios.

### 🔴 Hito 2 — El fail-fast es inerte · **CRÍTICO**

Falla por dos razones independientes; **ambas** hay que corregir.

#### 2a. El 402 nunca se convierte en excepción

`hikerapi_client._get()` clasifica: 429 → `SourceUnavailable`; 404 → `None`; 401/403 → `SourceUnavailable`; ≥500 → `TransientSourceError`. **El 402 no aparece.** Cae en `response.raise_for_status()`, que lanza `httpx.HTTPStatusError`, y el manejador hace:

```python
except httpx.HTTPStatusError as e:
    status = e.response.status_code
    if status >= 500:
        ...
    logger.error("hikerapi_http_error", ...)
    return None          # ← el 402 termina aquí
```

En todo el repositorio, `402` aparece **una sola vez: en un comentario de docstring** de `exceptions.py`. Nunca en una condición.

**El comportamiento con saldo agotado es idéntico al de antes del hito 2:** llamadas devuelven `None`, el pipeline continúa, el run cierra "completado" con 0 candidatos.

**Fix:**
```python
if response.status_code == 402:
    raise SourceUnavailable(
        f"402 Sin créditos — {response.text[:200]}",
        status_code=402, provider="hikerapi",
    )
```
Mejor aún, tratar en bloque: `if response.status_code in (401, 402, 403):`.

#### 2b. `asyncio.gather(return_exceptions=True)` anula los `raise`

Cada `_fetch_stepN` reenvía correctamente con `except SourceUnavailable: raise`. Pero los tres `gather` del worker usan `return_exceptions=True`, que **convierte la excepción en un valor de retorno**. Y el código siguiente hace exactamente lo que el hito quería eliminar:

```python
if isinstance(step1_result, Exception):
    logger.error("step1_hashtag_failed", error=str(step1_result))
    print(f"[STEP1] FAILED: {step1_result}")
else:
    hashtag_items = step1_result
```

Registra y continúa con lista vacía. El `except SourceUnavailable` de nivel superior (línea 1413), que está bien escrito, **es inalcanzable desde la fase de búsqueda**.

Lo mismo en el enrichment: `enrichment_results` se filtra con `isinstance(p, dict)`, así que los objetos `SourceUnavailable` se descartan en silencio y se llega a `if not enriched_profiles: step3_degraded = True` → *"Continuando con datos básicos"*.

**Fix:** tras cada `gather`, comprobar el tipo y re-lanzar:

```python
for res in (step1_result, step2_result):
    if isinstance(res, SourceUnavailable):
        raise res          # deja que el handler de nivel superior actúe
```
Los `TransientSourceError` sí pueden seguir degradando; sólo `SourceUnavailable` debe abortar.

### 🟠 Hitos 3+4 — El fusible mensual funciona; el límite por run no

**Funciona:** `assert_budget_available()` se llama al inicio del run (worker:193) y `BudgetExhausted` se maneja bien, con mensaje accionable y enlace de facturación. El corte mensual es real.

**No funciona — `MAX_CALLS_PER_RUN=120` es letra muerta.** `BudgetFuse` expone `can_make_call()` y `check_run_limit()`, y **ninguna de las dos se invoca en el worker**. Sólo se llama `record_call()`. El contador incrementa, nadie lo consulta, nada se detiene en 120.

**Fix:** consultar dentro de `_enrich_one()` antes de la llamada:
```python
if not await budget_fuse.can_make_call(run_id):
    raise BudgetExhausted(f"Límite de {settings.MAX_CALLS_PER_RUN} llamadas alcanzado", ...)
```

**Segundo problema — el contador subestima el gasto.** `record_call()` sólo se ejecuta en el enrichment (worker:826). Las ~20 llamadas de la fase de búsqueda (hashtags, keywords, reels, topsearch, suggested) **no se registran**. El acumulado mensual va corto entre un 15% y un 25%, y el corte al 100% ocurrirá cuando en realidad ya gastaste ~$12.

**Fix correcto:** registrar en el propio cliente, dentro de `_get()`, donde pasa toda llamada. Eso exige que el cliente conozca el `run_id` — pásalo como parámetro (y de paso resuelves el acoplamiento por atributo mutable que ya señalé en la primera auditoría).

**Tercero — `reset_run_counter()` nunca se llama.** Las claves `lens:budget:run:{run_id}` quedan con TTL de 24 h. No es grave, pero es un método muerto.

### 🟠 Circuit breaker — responde tu pregunta 2

**Tu pregunta:** *"se instancia DENTRO de `_get()` — ¿crea estado nuevo por llamada o comparte vía Redis?"*

**El estado sí se comparte correctamente.** Las claves son globales (`lens:cb:hikerapi:state`), no dependen de la instancia. Funcionalmente es correcto.

**Pero hay un costo oculto:** cada instancia crea su propio pool de conexiones en `_get_redis()` y **nunca se cierra** (la clase no tiene `close()`). Instanciar por llamada, con 120 llamadas por run, significa 120 pools de Redis huérfanos por run. Es una fuga de recursos que en Railway se manifiesta como agotamiento de conexiones bajo concurrencia.

**Fix:** instancia única a nivel de módulo, igual que `apify_client`:
```python
_breaker = HikerAPICircuitBreaker(provider="hikerapi")
```

**Tres problemas más del breaker:**

1. **HALF_OPEN es código muerto.** `_set_state` guarda el estado OPEN con `setex(..., breaker_ttl_s)` — la clave **expira** a los 300 s. Y `can_proceed()` transiciona a HALF_OPEN cuando han pasado ≥300 s. La clave desaparece antes o justo cuando la transición debería dispararse, así que `_get_state()` devuelve CLOSED por ausencia de clave. El circuito nunca pasa por HALF_OPEN: salta de OPEN a CLOSED de golpe, sin la llamada de prueba cautelosa que el diseño describe. **Fix:** darle a la clave un TTL mayor que `breaker_ttl_s` (p. ej. ×3).

2. **Hay dos copias divergentes del archivo** — `packages/discovery/discovery/tools/hikerapi_circuit_breaker.py` y `apps/api/app/core/hikerapi_circuit_breaker.py`. Verifiqué: **no son idénticas.** El cliente usa una, el worker la otra. Comparten claves de Redis, así que hoy funcionan igual, pero cualquier corrección aplicada a una sola creará una divergencia de comportamiento imposible de diagnosticar. **Fix:** dejar una sola en `packages/discovery` e importarla desde el worker.

3. **`HIKERAPI_5XX_BREAKER_THRESHOLD` y `HIKERAPI_5XX_BREAKER_TTL_S` no se usan.** Están definidas en `config.py:90-91`, y las dos instanciaciones del breaker (`worker.py:190` y dentro de `_get()`) lo construyen sin pasar `config`, así que siempre corren con los defaults de la dataclass (5 y 300). Ajustar esas variables en Railway hoy no tiene ningún efecto.

## 2. RESPUESTAS A TUS PREGUNTAS

**3. ¿Si una excepción ocurre entre `assert_budget_available()` y `record_call()`, no se registra el costo? ¿Es un bug?**

Sí, y es peor de lo que planteas. `record_call()` está *después* de `enrich_profile()`, así que si la llamada HTTP se hace y luego falla el procesamiento, el costo se pierde. Pero el agujero grande es el estructural: **la fase de búsqueda entera no registra nada** (§Hitos 3+4). El registro debe vivir en `_get()` del cliente, que es el único punto por el que pasan todas las llamadas.

**4. ¿ARQ deduplica jobs completados? Si un run falla y se reintenta manualmente, ¿se permite?**

ARQ mantiene el `_job_id` en Redis durante `keep_result` (default 3600 s). Mientras esté ahí, re-encolar con el mismo id devuelve `None` sin encolar — incluso si el job ya terminó o falló. **Con `_job_id=discovery:{run_id}`, un reintento manual del mismo run dentro de la hora siguiente se rechaza en silencio.**

Como cada reintento en tu flujo crea un `run_id` nuevo, en la práctica no molesta. Pero si añades un botón "reintentar este run", tendrás que incluir un discriminador: `_job_id=f"discovery:{run_id}:{attempt}"`.

**5 y 6. ¿Por qué falla `geo_score` con perfiles CO? ¿El problema está en la función o en el test?**

**En la función.** Aquí está la traza con `country="CO"` y `geo_indicators=["bogota","medellin"]`:

```python
target_iso2 = None
for iso2 in _ISO2_PATTERNS:
    if any(iso2.lower() == c.lower() for c in geo_indicators if len(c) == 2):
```

El filtro `if len(c) == 2` sólo mira indicadores de **dos caracteres**. `["bogota","medellin"]` no tiene ninguno → `target_iso2` queda en `None` → las dos ramas que usan el campo `country` no se ejecutan → se cae al emparejamiento textual sobre `search_text`, que se construye **sólo con bio, nombre, usuario y ubicación**. El campo `country` no entra ahí. Con la bio vacía del test, el resultado es 0.0.

**La raíz:** el país objetivo se *infiere* de que `geo_indicators` contenga un código ISO de dos letras. El generador de `DiscoveryProfile` produce `"colombia"`, `"bogota"`, `"colombiano"` — **nunca `"CO"`**. Así que `target_iso2` es `None` prácticamente siempre, y **toda la lógica del campo `country` es código muerto en producción**, no sólo en el test.

Es la misma corrección que quedó a medias en la primera auditoría: se arregló la descalificación indebida, pero no se cambió la firma. El país objetivo debe **pasarse explícitamente**, no adivinarse:

```python
def geo_score(profile: dict, geo_indicators: list[str], target_country: str | None = None) -> float:
    ...
    if target_country and country:
        return 1.0 if country == target_country.upper() else 0.0
```

Y el worker ya tiene el dato a mano: `brief.audience_countries[0]`.

**7. ¿Cómo recalibrar los scores?**

No los recalibres todavía. Con el prefiltro alimentándose de perfiles sin bio ni seguidores (§3), cualquier calibración se está ajustando a ruido. El orden correcto es: arreglar la firma de `geo_score` → arreglar qué llega al prefiltro → **medir con datos reales** → y sólo entonces ajustar pesos.

**8. ¿Cómo externalizar el vocabulario sin romper el pipeline?**

Incremental, con fallback, en tres pasos:
1. Añade los campos al `DiscoveryProfile` (`store_keywords`, `creator_keywords`, `geo_negative_keywords`) y al prompt del generador.
2. En el worker, `vocab = profile_data.get("store_keywords") or _STORE_KEYWORDS_FALLBACK` — las listas actuales pasan a ser el respaldo, no la fuente.
3. Cuando los perfiles generados demuestren calidad equivalente en el vertical de mascotas, reduce el fallback a un mínimo genérico.

Así nunca hay un momento en que el pipeline quede sin vocabulario.

**9. ¿Columna `state` o Redis para el orchestrator?**

**La columna `state`.** Ya existe, es duradera, y una conversación puede vivir días — Redis es para datos efímeros y aquí perderías el estado ante un reinicio o un desalojo por memoria. El dict en memoria se conserva como caché de lectura; la escritura va a Postgres en cada transición. Rehidratas cuando falla el lookup en memoria.

**10. Multi-tenancy: ¿filtrado en queries o rol separado?**

**Filtrado explícito por `business_unit_id` en la aplicación**, y no confíes en RLS con el usuario propietario. Razones prácticas: es incremental (tabla por tabla), es depurable, y no exige cambiar la gestión de credenciales de Railway. RLS con un rol de aplicación distinto es más robusto a largo plazo, pero implica un segundo rol, gestión de `SET LOCAL` por transacción y un pool separado — demasiada superficie para el punto en que estás. Lo importante es **dejar de documentar que existe aislamiento cuando no existe**.

**11. ¿Qué resolver antes de un segundo cliente?**

Bloqueantes: los hitos 5, 2 y 3+4 de esta lista (sin ellos ni siquiera el primer cliente funciona), el multi-tenancy, y el vocabulario hardcodeado (sin eso, cada cliente nuevo exige editar Python). El estado del orchestrator es tolerable con un cliente; con varios se vuelve visible.

**12. ¿Modo replay? ¿Cómo?**

Sí — es la mejor inversión de la lista después de los bloqueantes. La mayor parte de los $50-72 se gastó iterando lógica de scoring, que no necesita datos frescos.

Implementación mínima: `RUN_MODE=replay` como variable de entorno. En modo replay, `_get()` sólo lee de Redis y, si no hay dato cacheado, lanza `ReplayMiss` en vez de llamar a la red. Antes, un run normal con `cache_ttl` largo deja el dataset grabado. A partir de ahí iteras scoring gratis e infinitamente.

Si quieres persistencia entre reinicios de Redis, `pytest-recording` / `vcrpy` graba las respuestas HTTP en archivos y hace lo mismo dentro de los tests.

**13. ¿Dashboard mínimo viable?**

Cuatro números por run, y nada más al principio: **costo** (llamadas y USD por fase), **embudo** (cuántos perfiles entran y salen de cada etapa, con el motivo de descarte), **aporte por fuente** (candidatos finales que aportó cada fuente — es la métrica que te dice cuál apagar) y **fiabilidad** (errores por tipo, separando 402/429/5xx).

Con `api_costs` y Prometheus ya tienes de dónde. Pero lo que necesitas no es un gráfico: es la **alerta** al 70% y el corte al 100%. El gráfico puede esperar.
